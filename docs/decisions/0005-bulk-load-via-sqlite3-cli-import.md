# 0005 — Catalog bulk load shells out to the sqlite3 CLI

- Status: accepted
- Date: 2026-07-02 (backfilled 2026-07-08)

## Context

All database access was moved from shell-based SQLite to `sqlight` with
parameterized queries and typed decoders, eliminating SQL-injection risk from
string-built statements. One operation resisted the migration: the catalog
refresh bulk-loads the ~90k-row Scryfall CSV dump, and row-by-row
parameterized inserts are meaningfully slower than the `sqlite3` CLI's
`.import` at that volume.

## Considered options

- **Parameterized inserts like everything else** — uniform, injection-safe by
  construction, but the safety argument doesn't apply here (the input is our
  own `scryfall_mapper` output, not user-supplied text) while the speed cost
  is real at ~90k rows per refresh.
- **Keep `.import` for this one path** — one documented exception to the
  no-raw-SQL rule, bounded to a single DAO function.

## Decision

`catalog_dao.bulk_load` shells out to `sqlite3 .import`; everything else goes
through `sqlight`. The exception is documented as a rule in
`server/src/card_catalog/AGENTS.md` — don't "fix" it back to parameterized
inserts.

## Consequences

- Fast catalog refresh at dump scale.
- The runtime image must ship the `sqlite3` CLI, and this one path bypasses
  `sqlight`'s typed layer — acceptable only while the input stays
  machine-generated by us; if user-supplied data ever flows into bulk load,
  this ADR is superseded.
